How it works

Every serious simulated-user system converges on the same four layers. This skill implements them natively in Claude Code — no separate app, no separate API billing:

1 · Persona ingestion

Real research (or a described audience) becomes a structured persona file with behavioral fields that actually drive simulation.

2 · Agent embodiment

Each persona becomes an isolated agent that knows nothing about your design's intent — only who it is and what it's trying to do.

3 · Browser driving

The agent experiences your prototype through a real browser — clicking, scrolling, reading (or skimming) — in character, thinking aloud.

4 · Synthesis

Traces from all personas merge into an evidence-weighted findings report with verbatim quotes and a non-removable limitations footer.

The isolation is the point: a persona agent is spawned with only its persona file and standing instructions. It cannot see your conversation, your rationale, or what you hoped it would find — which is what keeps the testing honest.

Inspired by UXAgent (Amazon Science / CHI 2025), rebuilt as a portable, skill-native workflow.

Install

Requires Claude Code.

git clone https://github.com/jhoard/ux-personas.git
ln -sfn "$(pwd)/ux-personas" ~/.claude/skills/ux-personas
mkdir -p ~/.claude/personas

That's it. The skill auto-registers on your next Claude Code session (or immediately in a running one). Verify with /ux-personas.

Why a symlink? The repo stays git-managed wherever you keep code, while Claude Code sees it at the path it expects. git pull in the clone updates the live skill.

Quick start

1Create a persona. In Claude Code, from any project:

/ux-personas create a persona from my interview notes in research/interviews.md

2Serve a prototype. Any local HTML works:

python3 -m http.server 8080 --directory ./prototypes

3Run a test:

/ux-personas test http://localhost:8080/checkout.html with maria and raj — task "Find and change the shipping address"

4Read the report at ux-tests/<date>-<task>.md — outcomes per persona, ranked findings with verbatim think-aloud quotes, divergences between personas, and expert-lens observations.

You don't need the slash command — natural phrasing works: "test this flow with my personas", "import the personas from this old deck".

Creating personas

One entry point, three routes, chosen by what you actually have. Every persona is stamped with provenance so speculation never masquerades as research:

You haveProvenanceWhat happens
Interview notes, transcripts, surveys, support ticketsresearchThe skill extracts behavioral evidence, proposes distinct persona clusters, and builds the ones you pick. Every simulation field cites evidence or is marked (inferred). Verbatim participant quotes are preserved.
Existing persona docs (any format)importedRestructured into the schema. Classic marketing personas usually lack the behavioral fields — the skill asks you to fill each gap. Defaults to confidence: medium.
Just a description ("solo contractors, 40s, low tech fluency")generatedDrafts personas, asks sharpening questions for uncertain fields. Locked to confidence: low — never silently upgraded.

Personas save to a global library (~/.claude/personas/, reusable everywhere) or a project folder (./personas/, self-contained and handable to a client). A project persona with the same name shadows the global one.

The persona schema

One persona = one Markdown file. The frontmatter fields exist because they change agent behavior in a test — not for documentation decoration:

---
name: maria-the-overbooked-owner
display_name: Maria Delgado (invented)   # marked when sources are anonymized
archetype: Delegated admin
provenance: research        # research | imported | generated
confidence: high            # high | medium | low
sources:
  - interviews/2026-07-admin-study.md
created: 2026-08-18
client: MedCorp             # optional engagement tag
# --- simulation-critical fields ---
tech_fluency: low           # low | medium | high
patience: low - gives up after ~2 failed attempts
reading_style: skims        # skims | scans-headers | reads-thoroughly
domain_knowledge: expert in her trade, novice in software vocabulary
accessibility: reading glasses; small tap targets are a real problem
---

## Goals
## Frustrations        (verbatim quotes when research exists)
## Behavioral notes    ("abandons rather than create an account")
## Context

How fields drive behavior

FieldIn a test run…
tech_fluency: lowOnly labeled, conventional controls register as clickable. Unlabeled icons ("⋯", gear glyphs, hover-revealed menus) are invisible in practice. Jargon confuses, spoken aloud.
tech_fluency: highExpects RBAC, audit logs, bulk actions in conventional places; uses search first; reads errors fully. Also skips wizards, resents hand-holding, and flags what's missing — absent confirmations, missing audit trails.
patienceTreated literally. Exploratory clicks count as failed attempts. Giving up is a valid outcome — and a finding.
reading_style: skimsBody copy and helper text effectively don't exist. Buried CTAs go unfound.
reference_tools (extension)Expectations transfer: "in Okta this is on the user detail page — I checked there twice."

Running tests

/ux-personas test <url> with <personas> — task "<the flow to attempt>"
  • Preflight: personas validated, URL checked (the skill offers to serve a local folder if you gave a file path). Failures stop the run — the skill never "tests" from imagination.
  • One isolated agent per persona, run in parallel, each capped at 25 browser actions.
  • Outcomes: completed · gave-up (a finding!) · blocked · incomplete (technical) (not a finding — a harness problem, disclosed separately).

Anatomy of a report

SectionWhat it tells you
Run summaryPer-persona outcome, steps, stall point — with provenance/confidence labels so "blocked (research/high)" reads differently from "blocked (generated/low)".
FindingsFriction clustered across personas, ranked by (personas affected × confidence), each citing verbatim think-aloud.
DivergencesWhere personas behaved differently and why that's informative ("Raj completed via search; Maria never discovered search exists").
Expert-lens findingsGovernance and trust gaps — missing confirmations, audit trails, bulk actions — kept separate because they route to different fixes.
Limitations footerFixed, non-removable. See below.

See a real one: examples/sample-findings-report.md — from the skill's own acceptance run, where a low-fluency persona correctly gave up on a hover-only menu and a high-fluency admin flagged the missing audit trail.

Client engagements

The schema is deliberately two-layer: a universal core (how any human behaves at an interface) plus a free-form attributes: extension per engagement. Declare what a client's personas must capture in personas/_schema.md and every creation flow will prompt for it.

The repo ships a starter for enterprise governance/admin work — copy starters/enterprise-governance.md to your project's personas/_schema.md to capture:

role_scope          # what they administer
permissions_level   # global admin | delegated admin | auditor | end user
compliance_context  # SOC2, HIPAA, FedRAMP...
risk_posture        # "blocks first" vs "enables, monitors"
approval_chain      # can they act unilaterally?
reference_tools     # Okta, ServiceNow... expectations transfer from these

A persona who can't act unilaterally tests flows differently — they hunt for export and share-for-approval paths, and their absence becomes a finding no consumer-style persona would surface.

Does the simulation actually work?

A persona's fields are only worth having if they change what the agent does — and only trustworthy if they haven't been tightened so far the persona can't succeed at anything. verify proves both.

For a trait, it builds two personas identical except that trait, set to opposing poles, runs each against an arena whose outcome the trait should decide, and has a judge on a different model read each trace and return expressed, correctly-suppressed, or violated. Passing requires both arms correct:

ResultMeaning
Both arms correctBinding and not over-tight — ship
Constrained arm succeeds anywayThe rule is decoration, not behavior — tighten it
Capable arm fails tooThe rule is crippling the persona — loosen it

That third row is what a single-arm check cannot see, and it is the failure mode that turns a testing instrument into a machine that manufactures findings. Shipped pairs cover tech_fluency, reading_style, and patience. domain_knowledge and accessibility are documented as not yet fixture-testable — a check that cannot fail is worse than no check.

Method adapted from MatrAIx, which validated persona-agent behavior across 400 controlled trials (91.5% adherence).

Honest limitations

Simulated users are not research participants. They cannot experience real emotion, produce genuinely novel behavior, or represent statistical prevalence. They are documented to be unreliable for concept validation (they tend to praise concepts). Every report this skill produces carries this warning, non-removably — including reports that end up in client deliverables.

Where they're genuinely strong: early flow and findability testing ("can this persona complete the task?" is behavioral, not attitudinal), cheap iteration between design revisions, and piloting studies before you spend real-participant time. Validate any expensive decision with real users.

Portability

Everything except SKILL.md is harness-agnostic prose — persona files, agent instructions, report templates. Porting to another agent harness means rewriting one orchestration page. Your persona library is plain Markdown that any tool (or human) can read.
